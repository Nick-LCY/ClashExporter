# 0002. 无损淘汰与重锚

- 日期：2026-10-26
- 状态：已接受
- 修订：2026-10-26 增补 `prune_ttl` 无损裁剪（实现与审查修正阶段追加）。
- 背景：
  核心指标的每条序列对应一个「设备 × 站点 × 节点」组合。长期运行后历史站点与历史设备组合不断累积，Prometheus 侧的存储与查询成本持续上涨；但如果为了控制基数直接丢弃序列，又会制造统计缺口——序列一旦从 `/metrics` 消失，Prometheus 计算 `increase()` 时只能覆盖缺口之前的部分，跨缺口的长期增量会被低估。矛盾在于既要控制基数，又不能丢数。
- 决策：
  - 某组合连续 24 小时（可配置 `evict_ttl`）没有新增字节时，将其标记为淘汰态并停止导出该序列；账本数据保留，不清零。
  - 该组合之后再次产生流量时重锚恢复导出：恢复后第一次导出的值恰好等于上次导出的值（`lastExported`），此后每轮在 `lastExported` 基础上继续累加新增量。
  - 因为恢复点的取值与消失前完全一致，Prometheus 端跨 stale 间隙的 `increase()` 不会丢失流量，缺口期的字节数在恢复时被补齐。
  - 停导不等于删数据：账本条目会随历史组合持续累积，因此再加一道 `prune_ttl`（默认 168h，可配置）清理——条目**已淘汰、无待导出增量、且静默超过 `prune_ttl`** 后从账本删除，快照随之不再包含。
- 影响：
  - 暴露面有界：稳态下导出的序列数不超过「最近 24 小时内有流量的组合数」，长期运行不会无界增长。
  - 实现上每个条目必须同时保存「已导出值」与「待导出增量」两个量；导出是写操作（要推进已导出值），不能使用只读锁。
  - 重锚逻辑被拆成两半：重新启用发生在归账阶段，第一次导出取上次导出值发生在导出阶段，采集器不得自行加减小计。
  - 计数器保持单调不减，这是 [[architecture/decisions/0001-单表全维度计数器.md]] 中计数器语义的一部分。
  - `prune_ttl` 清理是无损的：条目被淘汰时已连续 `evict_ttl` 没有新增字节，待导出增量为 0 意味着累计值已经完整导出（`total == lastExported`），删除只丢掉一段此后没有变化的历史值；该组合日后重现时以新基线重新计数，Prometheus 端按新序列处理，没有任何已观测字节丢失。
  - 带待导出增量或未到 `prune_ttl` 时限的活跃条目一律不删——那些字节还没报出去，删掉就是真丢；清理条件必须同时包含「已淘汰」与「待导出增量为 0」两项。
  - 账本内存占用因此有界：条目数最多为「最近 `prune_ttl` 内出现过的组合数」，不再随运行时长无限增长。
